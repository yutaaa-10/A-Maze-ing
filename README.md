# A-Maze-ing


## 概要 (Description)

A-Maze-ingは、Pythonで迷路を生成するプログラムです。

このプロジェクトの目的は、迷路生成を通してアルゴリズム、ランダム性、
グラフ理論、経路探索、データ表現などの概念を学ぶことです。

プログラムは設定ファイルから迷路の情報を読み込み、その設定に基づいて
迷路を生成します。また、入口から出口までの最短経路を求め、
迷路の壁を16進数で表現した出力ファイルを生成します。

さらに、迷路生成部分は他のPythonプロジェクトでも再利用できるように、
`mazegen` というPythonパッケージとして提供しています。

`flake8` と `mypy` をインストールします。

```bash
make install
```

### プログラムの実行

デフォルトの `config.txt` を使用する場合：

```bash
make run
```

内部では次のコマンドが実行されます。

```bash
python3 a_maze_ing.py config.txt
```

別の設定ファイルを使用する場合：

```bash
make run CONFIG=example.txt
```

Pythonの `pdb` を使用して実行します。


## 追加セクション (Additional sections)


###  設定ファイルの完全な構造と形式

迷路のサイズ、入口・出口、出力ファイル、Perfect は、config.txtから指定します。

リポジトリには、プログラムをすぐに実行できるデフォルトの
`config.txt` が含まれています。

#### 基本形式

設定ファイルは、1行につき1つの設定を以下の形式で記述します。

```text
KEY=VALUE
```

`#` から始まる行はコメントとして扱われ、プログラムから無視されます。

例：
```text
# Maze configuration
WIDTH=20
HEIGHT=15
ENTRY=0,0
EXIT=19,14
OUTPUT_FILE=maze.txt
PERFECT=True
```

#### ファイル構造

| キー | 形式 | 説明 | 例 |
| --- | --- | --- | --- |
| `WIDTH` | 整数 | 迷路の横幅（セル数） | `WIDTH=20` |
| `HEIGHT` | 整数 | 迷路の高さ（セル数） | `HEIGHT=15` |
| `ENTRY` | `x,y` | 迷路の入口となるセルの座標 | `ENTRY=0,0` |
| `EXIT` | `x,y` | 迷路の出口となるセルの座標 | `EXIT=19,14` |
| `OUTPUT_FILE` | 文字列 | 生成した迷路を書き込むファイル名 | `OUTPUT_FILE=maze.txt` |
| `PERFECT` | `True` / `False` | Perfect Mazeを生成するかを指定 | `PERFECT=True` |


### 選択した迷路生成アルゴリズム

再帰的バックトラック法（Recursive Backtracker）。深さ優先探索（DFS）を
迷路生成に用いたものです。

未訪問のセルへ進めるかぎり進み、進めなくなったら分岐点まで戻る、という
動作を繰り返します。本実装では再帰ではなく明示的なスタックを使い、
関数の呼び出しスタックが担う役割を自前のリストで管理しています。

「未訪問のセルにしか進まない」という規則から、生成される辺は必ず全域木に
なります。閉路の検査を別途行う必要はありません。

### この迷路生成アルゴリズムを選択した理由

保持する状態がスタック1本で済むためです。

Kruskal法はUnion-Find、Prim法は候補となる辺の集合を別途管理する必要が
あります。再帰的バックトラック法は、現在のスタックと訪問済み集合だけで
完結します。

生成される迷路の性質については、いずれの手法も全域木を作る点で共通です。
`PERFECT=True` の要件（入口から出口への経路がちょうど1本）は、どの手法を
選んでも満たせます。今回は実装の単純さを基準に選択しました。


### コードのどの部分が再利用可能で、どのように再利用できるのか。

#### コードの再利用性

このプロジェクトでは、迷路生成ロジックを `mazegen` パッケージとして
独立させています。設定ファイルの読み込み、ターミナル表示、コマンドライン
処理は `a_maze_ing.py` 側に置き、パッケージには含めていません。

パッケージは `.whl` または `.tar.gz` としてビルドでき、wheelの場合は
以下のようにインストールできます。

```bash
pip install mazegen-1.0.0-py3-none-any.whl
```

#### 公開しているもの

| 名前 | 種類 | 説明 |
| --- | --- | --- |
| `MazeGenerator` | クラス | 迷路を生成する |
| `Maze` | dataclass | 生成された迷路構造 |
| `get_shortest_path` | 関数 | 2点間の最短経路を返す |
| `to_hex` | 関数 | 迷路を16進表記に変換する |

#### 基本的な使い方

```python
from mazegen import MazeGenerator, get_shortest_path, to_hex

generator = MazeGenerator(20, 15)
maze = generator.generate(seed=42, perfect=False)

print(to_hex(maze))
print(get_shortest_path(maze, (0, 0), (19, 14)))
```

`MazeGenerator` は迷路のサイズだけを保持します。生成のたびに変わる値は
`generate()` に渡します。

| 引数 | 型 | 既定値 | 説明 |
| --- | --- | --- | --- |
| `seed` | `int \| None` | `None` | 乱数の種。同じ値なら同じ迷路が再現される |
| `perfect` | `bool` | `True` | `False` ならループを含む迷路 |
| `start` | `tuple[int, int]` | `(0, 0)` | 生成を開始するセル |
| `blocked` | `set[tuple[int, int]] \| None` | `None` | 通路として使わないセルの集合 |

#### 生成された構造へのアクセス

`generate()` は `Maze` を返します。`width`、`height`、`edges` を持ちます。

`edges` は通路の集合です。隣り合う2セルの座標を含む `frozenset` が
`edges` にあれば、その間は通行できます。なければ壁です。

```python
if frozenset({(3, 5), (4, 5)}) in maze.edges:
    ...  # (3,5) と (4,5) は行き来できる
```

`frozenset` を使っているため向きはなく、隣接セルの壁が食い違うことは
構造的に起こりません。

出力ファイルの16進表記とは独立しているため、`Maze` をそのまま別の
プログラムで扱うことも、`to_hex()` で変換することもできます。

#### `blocked` の使い方

`blocked` に渡したセルは生成前に訪問済みとして扱われ、通路が一切
つながりません。本プロジェクトではこれを使って「42」を描いています。

詳細は `mazegen/README.md` を参照してください。

#### 当初の計画と、それがどのように変化したか

当初は「まず動くものを作り、その後で整理する」という方針で進めました。
迷路が生成できてターミナルに表示されるところまでを先に作り、構造の
見直しはその後に回しました。

この方針自体は変えませんでしたが、整理の段階で当初想定していなかった
変更がいくつか発生しました。

- 生成器が保持していた作業用の状態（訪問済み集合、スタック、辺の集合）を
  `generate()` のローカル変数に移した。同一のインスタンスで複数回生成した
  ときに前回の状態が残る問題があったため。
- 迷路の構造を `Maze` という dataclass に切り出し、生成器とは独立した
  値として扱うようにした。
- 最短経路の探索と隣接セルの取得をクラスの外へ出した。これらは生成器の
  状態を必要としないため。
- 「42」パターンの生成をパッケージから `a_maze_ing.py` 側へ移し、
  代わりに `blocked` 引数で任意のセルを除外できるようにした。本課題固有の
  要件を再利用モジュールから分離するため

#### 上手くいった点と改善すべき点
・上手く行った点:
```text
書き進める中で、独立したモジュールとして外部に公開することを意識できる
ようになっていった点。

どの関数を公開し、どれを内部に留めるかを判断することで、その関数が
どこまでの入力を想定すべきかが決まる。公開する関数は呼び出され方を
制御できないため引数を検証する必要があり、内部専用の関数は呼び出し順を
自分たちで管理できるためその検査を省ける。この区別が実装の指針になった。

また、前々からいつかやらなきゃいけないと思いながら後回しにしていたgitでの共同開発プロセス
の理解も少し進められたことが良かった。
```

・改善すべき点:
```text
課題の要件を先に具体的に把握し、公開するインターフェースを定義してから
実装を始めるべきだった。

実装しながら関数のシグネチャを変更したため、実装の過程で理解を共有し続けるのが難しかった。
先に構造を決めておけば、齟齬を減らし、
互いに理解を共有しながら進められたと考えている。
```
